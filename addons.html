For developers

Building Add-ons

An add-on is a script that runs from TuneZinc's right-click menu. It gets a JSON payload of the selected track, album, artist, or playlist over stdin — and can do whatever you want with it.

Setup

Add-ons live in %USERPROFILE%\TuneZinc\addons\<addon_name>\. Each add-on is its own subfolder containing a manifest.json. The app scans TuneZinc/addons/*/manifest.json when you click "Scan Add-ons" in Settings, and on first launch.

manifest.json

{
  "displayName": "Debug: Echo Payload",
  "contexts": ["track", "tracks", "album", "artist", "playlist", "global"],
  "executable": "python",
  "scriptPath": "echo_test.py"
}
FieldMeaning
displayNameShown in the context menu.
contextsWhere the add-on appears. Values: track, tracks, album, artist, playlist, global. A single string "context": "track" also works (legacy).
executableBinary to run — python, or an absolute path to a bundled .exe.
scriptPathRelative to the add-on's own folder. Must stay inside it — no .., no absolute paths. The scanner rejects violations and skips the add-on silently.

Run flow

  1. User picks the add-on from the context menu.
  2. App builds a JSON payload for the context (see below).
  3. First run of a script — keyed by content hash, not path — pops a consent dialog the user must approve. Re-approval is required if the script content changes.
  4. App spawns executable scriptPath (no shell), writes the payload to stdin as one line plus a newline, then closes stdin.
  5. stdout/stderr stream live into the console view (Settings → running add-ons), capped at 300 lines / 2000 chars each.
  6. Non-zero exit code → stderr is dumped to error_out.txt in the add-on folder.
  7. If the add-on's entire stdout trims to a bare http:// or https:// URL, the app opens it in the default browser. Nothing else in stdout does anything — no file://, no custom schemes, deliberately blocked.

So: read stdin, do work, optionally print exactly one URL to stdout for the app to open, and write everything else to your own file if you want to inspect it (or use the debug console).

Payload shapes

Stdin is always a single JSON blob. Each track object carries: id/uuid, path, title, artist, album, albumArtPath, genre, recordingMbid, releaseMbid, bitrate, durationMs, year, trackNumber, discNumber, fileSizeBytes, isDeleted, createdAt — recommendationModelId and audioHash are stripped before sending.

track / tracks context

{ "tracks": [ {...track} ], "trackCount": 1 }

album context

{ "albumName": "...", "albumArtist": "...", "tracks": [...], "trackCount": N }

artist context

{ "artistName": "...", "tracks": [...], "trackCount": N }

playlist context

{
  "playlist": {
    "id": .., "name": .., "description": ..,
    "createdAt": .., "updatedAt": .., "lastListenedAt": ..,
    "isPinned": .., "pinnedOrder": .., "trackCount": ..
  },
  "tracks": [...],
  "trackCount": N
}

global context

Whatever's currently passed, or this fallback:

{"volume":0.75,"playbackStatus":"playing","tracks":[],"trackCount":0}

Minimal script (Python)

import sys, json

def main():
    data = json.loads(sys.stdin.read())
    # ... do work ...
    print(json.dumps({"status": "success"}))  # or print a bare URL to open it

if __name__ == "__main__":
    main()

See debug_echo/echo_test.py — dumps the full payload to debug_output.txt next to the script, handy for checking the exact shape the app sends for a given context. Download the debug_echo example add-on (.7z).

Notes

  • No payload as a CLI arg — stdin only.
  • Keep stdout small and clean if you want the app's snackbar/URL-launch behavior to stay sane — dump big debug data to your own file instead.
  • The add-on folder is writable by the script (error_out.txt, any output files) — same permissions as the user running TuneZinc.
  • Only install or run add-ons from sources you trust — an add-on can do anything its script can do with your local permissions.
